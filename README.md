# Сервис форм отклика

[![check](https://github.com/nata2627/futuretoday-forms/actions/workflows/ci.yml/badge.svg)](https://github.com/nata2627/futuretoday-forms/actions/workflows/ci.yml)

Менеджер собирает форму отклика в админке, публикует ее по неугадываемой ссылке и видит в отдельных вкладках ответы студентов и аналитику заполнения: сколько человек дошло до каждого шага, на каком вопросе обрывается заполнение, что именно не принимает сервер и сколько времени уходит на форму.

Node.js и express, одна зависимость, данные лежат в JSON-файлах внутри проекта.

## Запуск

Две команды из корня репозитория:

```
npm install
npm start
```

Сервис отвечает на `http://localhost:3000`, админка на `http://localhost:3000/admin`. Порт задается переменной окружения `PORT`, например `PORT=4000 npm start`. Нужен Node.js 20 или новее. Папка для данных создается при старте сама, готовить ничего не нужно.

## Проверка

```
npm test     # 23 теста на валидацию и на подсчет аналитики, встроенный node:test, без зависимостей
npm run check  # 26 шагов: поднимает сервис и проходит весь сценарий запросами
```

`npm run check` поднимает сервис на свободном порту в отдельной папке с данными, идет по пути менеджера и студента и падает с кодом 1 на первом сломанном шаге. Рабочие данные в `data/` он не трогает.

Оба прогона плюс отдельная проверка «две команды из чистого клона» идут в CI на Node 20, 22 и 24 при каждом пуше, файл `.github/workflows/ci.yml`.

Те же проверки руками:

```
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:3000
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:3000/f/doesnotexist
curl -s -o /dev/null -w "%{http_code}\n" -X POST http://localhost:3000/admin/forms --data-urlencode "title="
```

Первая команда дает 200, вторая 404, третья 400.

## Сценарий

1. Менеджер открывает `/admin`, называет форму и создает ее. Форма появляется черновиком.
2. Добавляет вопросы по одному: тип, подпись, подсказка под полем, обязательность, варианты. Вопросы можно переставлять, править и удалять, предпросмотр доступен до публикации.
3. Нажимает «Опубликовать» и получает ссылку вида `/f/<идентификатор>` с кнопкой «Скопировать».
4. Студент переходит по ссылке и заполняет форму. Над формой идет счетчик заполненных обязательных вопросов, ошибки показываются рядом с полями, введенное не теряется, черновик переживает случайное закрытие вкладки.
5. Менеджер смотрит вкладку «Ответы» (таблица и выгрузка в CSV) и вкладку «Аналитика».

## Типы вопросов

Десять типов, у каждого своя проверка на сервере: короткий текст, длинный текст, почта, телефон (считаются цифры), число (с необязательными границами), дата (проверяется существование даты, 31 февраля не пройдет), список, один вариант из нескольких, несколько вариантов, согласие одной галочкой.

Идентификаторы вопросов выдает сервер, браузеру это не доверяется. Поэтому вопрос можно переименовать или сделать необязательным, не потеряв уже собранные ответы, а значения, которых нет среди вариантов, в хранилище не попадают. Тип вопроса после создания не меняется: уже собранные ответы хранятся в его формате.

## Аналитика

В задании сказано, что студенты бросают заполнение на полпути, а причина низкой конверсии остается неизвестной. Вкладка «Аналитика» отвечает на этот вопрос пятью блоками. В каждом рядом с долей стоит знаменатель: процент без знаменателя на выборке в десяток человек ничего не значит.

| Блок | Что показывает | Чем измеряется |
|---|---|---|
| Воронка | открыли форму, начали заполнять, отправили отклик | события визита |
| Где остановились | последний вопрос, на котором видели студента, у тех, кто не отправил | сигнал браузера при закрытии вкладки |
| Что сервер не принял | по каждому вопросу: сколько визитов получили отказ валидации | серверные события, счет полный |
| Сколько времени уходит | медиана от открытия до отправки, медиана до первого ввода, попыток на один принятый отклик | события визита |
| Что выбирают | распределение ответов по вариантам списков и галочек | сами ответы |

Что считается визитом: одно открытие публичной страницы. Сервер кладет в страницу случайный идентификатор визита и пишет события `opened`, `started`, `attempt`, `rejected`, `submitted` и отметку о последнем вопросе. В событиях нет куки, адресов, заголовков браузера и ничего о человеке, идентификатор визита живет только в этой странице.

Где честные границы метода:

- Событие «начал заполнять» требует JavaScript, а отправка работает и без него, поэтому отправка засчитывается и как начало заполнения. Иначе воронка показывала бы больше отправок, чем начавших.
- Отметка о последнем вопросе уходит при закрытии вкладки и тоже требует JavaScript, поэтому это нижняя оценка. Рядом с таблицей написано, у скольких ушедших она вообще получена.
- Отказы сервера считаются на каждой попытке отправки и не зависят от браузера, поэтому этот счет полный.
- Время считается медианой, а не средним: одна вкладка, забытая на сутки, сдвинула бы среднее и соврала бы о форме.

Идеи, которые в этот объем не вошли, но напрашиваются следующими: время на каждом отдельном вопросе, разрез по дням и источникам перехода, подсказка менеджеру «этот вопрос отклоняется чаще других, смягчите формат», сравнение двух версий одной формы.

## Устройство

| Файл | Что в нем |
|---|---|
| `src/server.js` | маршруты и запуск, порт из `PORT` |
| `src/storage.js` | чтение и запись JSON-файлов в `data/` |
| `src/validation.js` | проверка схемы формы, вопроса и ответа студента |
| `src/analytics.js` | подсчет воронки и остальных метрик по событиям |
| `src/views.js` | публичные страницы, экранирование вывода |
| `src/admin-views.js` | страницы админки |
| `src/csv.js` | выгрузка ответов |
| `public/` | стили, копирование ссылки, счетчик заполнения и отправка событий |
| `tests/` | тесты на валидацию и на аналитику |
| `scripts/check.mjs` | проверка сценария целиком |

Форма хранится так: `{ id, title, description, fields: [{ id, type, label, hint, required, options, min, max }], published, createdAt, updatedAt }`. Идентификатор формы это 16 случайных байт в base64url, он же адрес публичной ссылки, перебрать его нельзя. Ответ: `{ id, formId, visitId, values: { идентификатор вопроса: значение }, createdAt }`.

Вся валидация живет на сервере. Админка и публичная форма отправляются обычным HTML-запросом и работают с выключенным JavaScript. JavaScript делает только то, без чего можно обойтись: копирует ссылку, прячет в конструкторе поля, ненужные выбранному типу, считает заполненные обязательные вопросы, хранит черновик в браузере студента и шлет события аналитики. Черновик лежит в `localStorage` самого студента, на сервер не уходит и стирается после отправки.

## Почему JSON-файл, а не SQLite

Главный критерий задания это запуск двумя командами на чужой машине, поэтому хранилище выбиралось по риску установки, а не по удобству запросов. `better-sqlite3` собирается нативно и ломает `npm install` там, где нет готовой сборки, а встроенный `node:sqlite` появился только в Node 22, тогда как задание разрешает Node 20. JSON-файл снимает оба риска и прямо назван в задании как допустимый вариант. Чем он хуже: нет запросов и индексов, файл читается целиком, на тысячах ответов это станет заметно. Для одного проверяющего и десятков ответов разницы нет.

Формы, ответы и события лежат в отдельных файлах в `data/`, поэтому растущий файл событий не переписывает формы. Запись идет во временный файл с последующим `rename`, а записи в один файл выстроены в очередь: без этого две одновременные отправки прочитали бы одно состояние и вторая затерла бы первую. Проверено 25 одновременными записями, все 25 на месте.

## Что сознательно не делалось

| Чего нет | Почему |
|---|---|
| Авторизации в админке | задание прямо требует админку без авторизации. Для продакшена это первое, что нужно закрыть |
| Смены типа у созданного вопроса | уже собранные ответы хранятся в формате этого типа, корректная смена требует версионирования схемы и миграции ответов. Подпись, подсказка, обязательность и варианты меняются свободно |
| Перетаскивания вопросов мышью | порядок меняется кнопками, обычной отправкой формы. Перетаскивание потребовало бы JavaScript там, где сейчас без него все работает |
| Защиты от повторной отправки | один студент может отправить отклик дважды, в таблице будет две записи. Честная дедупликация требует входа студента |
| Загрузки файлов, например резюме | хранение файлов это отдельный разговор про размер, типы и безопасность, а ключевой сценарий закрывается ссылкой в текстовом вопросе |
| Деплоя | задание требует локальный запуск двумя командами и запрещает внешние сервисы |

## Ограничения

Сервис рассчитан на один процесс: очередь записи живет в памяти, при запуске двух копий на одной папке данных файлы можно испортить. Все формы и ответы доступны любому, кто открыл `/admin`, это следует из требования задания. Размер тела запроса ограничен 128 КБ, значение вопроса 2000 символами (длинный текст 4000), вопросов в форме не больше 30. Выгрузка CSV идет через запятую в UTF-8 с меткой кодировки: Excel открывает такой файл с кириллицей верно.
