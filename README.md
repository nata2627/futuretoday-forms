# Сервис форм отклика

Менеджер собирает форму отклика в админке, публикует ее по неугадываемой ссылке и видит в админке ответы студентов и воронку заполнения: сколько человек открыли форму, сколько начали ее заполнять и сколько отправили.

Тестовое задание. Node.js и express, одна зависимость, данные лежат в JSON-файлах внутри проекта.

## Запуск

Две команды из корня репозитория:

```
npm install
npm start
```

Сервис отвечает на `http://localhost:3000`, админка на `http://localhost:3000/admin`. Порт задается переменной окружения `PORT`, например `PORT=4000 npm start`. Нужен Node.js 20 или новее. Папка для данных создается при старте сама, готовить ничего не нужно.

## Проверка

```
npm run check
```

Скрипт поднимает сервис на свободном порту в отдельной папке с данными, проходит ключевой сценарий запросами и печатает шаги. Шагов 20, падает с кодом 1 на первом сломанном. Рабочие данные в `data/` он не трогает. Что именно проверяется: запуск, пустое состояние админки, отказ на форме без названия, отказ на публикации формы без полей, отказ на поле выбора без вариантов, публикация и ссылка, экранирование подписи поля, отказ на пустом обязательном поле с сохранением введенного, отказ на неверной почте, успешная отправка, ответ в админке, сходимость воронки, 404 на чужую ссылку, на выход из папки данных и на снятую с публикации форму, удаление формы вместе с ее ответами и событиями.

Те же проверки руками:

```
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:3000
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:3000/f/doesnotexist
curl -s -o /dev/null -w "%{http_code}\n" -X POST http://localhost:3000/admin/forms --data-urlencode "title="
```

Первая команда дает 200, вторая 404, третья 400.

## Сценарий

1. Менеджер открывает `/admin`, называет форму и создает ее. Форма появляется черновиком.
2. Добавляет поля по одному: подпись, тип (короткий текст, длинный текст, почта, выбор из списка), обязательность. Для выбора из списка перечисляет варианты по одному в строке.
3. Нажимает «Опубликовать» и получает ссылку вида `/f/<идентификатор>` с кнопкой «Скопировать».
4. Студент переходит по ссылке, заполняет форму и отправляет. Ошибки показываются рядом с полями, уже введенное не теряется.
5. Менеджер видит на странице формы таблицу ответов и воронку заполнения.

## Устройство

| Файл | Что в нем |
|---|---|
| `src/server.js` | маршруты и запуск, порт из `PORT` |
| `src/storage.js` | чтение и запись JSON-файлов в `data/` |
| `src/validation.js` | проверка схемы формы, поля и ответа студента |
| `src/funnel.js` | подсчет воронки по событиям |
| `src/views.js` | сборка HTML, весь вывод через `escapeHtml` |
| `public/` | стили, кнопка копирования ссылки, отправка события о первом вводе |
| `scripts/check.mjs` | проверка ключевого сценария |

Форма хранится так: `{ id, title, description, fields: [{ id, label, type, required, options }], published, createdAt }`. Идентификатор формы это 16 случайных байт в base64url, он же и адрес публичной ссылки, перебрать его нельзя. Идентификаторы полей выдает сервер, браузеру это не доверяется: иначе два поля с одинаковым именем затирали бы ответ друг друга. Ответ хранится как `{ id, formId, values: { идентификатор поля: значение }, createdAt }`, поля, которых нет в схеме, отбрасываются при приеме.

Вся валидация живет на сервере. Админка и публичная форма отправляются обычным HTML-запросом и работают с выключенным JavaScript, атрибуты `required` и `type=email` в разметке нужны только для того, чтобы студент увидел ошибку раньше. JavaScript в проекте делает ровно две вещи: копирует ссылку в админке и сообщает о первом вводе в публичную форму.

## Воронка заполнения

В задании сказано, что студенты бросают заполнение на полпути, а причина низкой конверсии остается неизвестной. Поэтому на странице формы в админке стоят три числа: открыли форму, начали заполнять, отправили отклик. Доли показаны со знаменателем рядом («5 из 8»), потому что на выборке в несколько человек один процент без знаменателя ничего не значит. Под таблицей одна строка словами о том, где теряется больше: на входе или в середине.

Как считается: при открытии публичной страницы сервер кладет в нее случайный идентификатор открытия и пишет событие `opened`. Скрипт на странице один раз сообщает о первом вводе в любое поле, это событие `started`. Успешная отправка дает событие `submitted`. События лежат в `data/events.json`, одно событие на открытие и тип.

Чего в событиях нет: куки, IP-адресов, заголовков браузера, любых данных о человеке. Идентификатор открытия случайный и живет только в этой странице.

Ограничение, о котором стоит знать: событие «начал заполнять» требует JavaScript, а отправка работает и без него. Поэтому отправка засчитывается и как начало заполнения. Без этого правила воронка показывала бы больше отправок, чем начал, то есть была бы просто неверной.

## Почему JSON-файл, а не SQLite

Главный критерий задания это запуск двумя командами на чужой машине, поэтому хранилище выбиралось по риску установки, а не по удобству запросов. `better-sqlite3` собирается нативно и ломает `npm install` там, где нет готовой сборки, а встроенный `node:sqlite` появился только в Node 22, тогда как задание разрешает Node 20. JSON-файл снимает оба риска и прямо назван в задании как допустимый вариант. Чем он хуже: нет запросов и индексов, файл читается целиком, на тысячах ответов это станет заметно. Для одного проверяющего и десятков ответов разницы нет.

Формы, ответы и события лежат в отдельных файлах в `data/`, поэтому растущий файл ответов не переписывает формы. Запись идет во временный файл с последующим `rename`, а записи в один файл выстроены в очередь: без этого две одновременные отправки прочитали бы одно состояние и вторая затерла бы первую. Проверено 25 одновременными записями, все 25 на месте.

## Что сознательно не делалось

| Чего нет | Почему |
|---|---|
| Авторизации в админке | задание прямо требует админку без авторизации. Для продакшена это первое, что нужно закрыть |
| Редактирования полей опубликованной формы | ответы уже собраны по текущей схеме, корректная правка требует версионирования схемы и миграции ответов. Поля можно добавлять и удалять, но ответы показываются по текущей схеме формы |
| Типов полей сверх четырех | четыре типа закрывают форму отклика целиком, а каждый новый тип это еще одна ветка в валидации и в отрисовке |
| Выгрузки ответов в CSV | менеджеры живут в таблицах, но это надстройка над готовым экраном ответов, а не часть ключевого сценария |
| Защиты от повторной отправки | один студент может отправить отклик дважды, в таблице будет две записи. Честная дедупликация требует входа студента |
| Набора тестов | вместо него один скрипт `npm run check`, который проходит сценарий целиком. На объеме этой задачи он ловит те же поломки дешевле |
| Деплоя | задание требует локальный запуск двумя командами и запрещает внешние сервисы |

## Ограничения

Сервис рассчитан на один процесс: очередь записи живет в памяти, при запуске двух копий на одной папке данных файлы можно испортить. Все формы и ответы доступны любому, кто открыл `/admin`, это следует из требования задания. Размер тела запроса ограничен 64 КБ, значение поля 2000 символами, полей в форме не больше 20.
