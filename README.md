# futuretoday-forms

Сервис форм отклика: менеджер собирает форму в админке, публикует ее по уникальной ссылке, студент заполняет форму по этой ссылке, менеджер видит ответы и воронку заполнения. Тестовое задание, стек Node.js и express, данные хранятся внутри проекта.

Статус: каркас и запуск готовы, сценарии дописываются. Разбор решения появится в этом файле.

## Запуск

Две команды из корня репозитория:

```
npm install
npm start
```

Сервис отвечает на `http://localhost:3000`, админка на `http://localhost:3000/admin`. Порт задается переменной окружения `PORT`, например `PORT=4000 npm start`. Нужен Node.js 20 или новее. Папка для данных создается при старте сама, готовить ничего не нужно.

## Проверка

```
npm run check
```

Скрипт поднимает сервис на свободном порту в отдельной папке с данными, проходит ключевой сценарий запросами и печатает шаги. Падает с кодом 1 на первом сломанном шаге. Рабочие данные в `data/` он не трогает.

Руками то же самое:

```
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:3000
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:3000/f/doesnotexist
```

Первая команда дает 200, вторая 404.

## Почему JSON-файл, а не SQLite

Главный критерий задания это запуск двумя командами на чужой машине, поэтому хранилище выбрано по риску установки, а не по удобству запросов. `better-sqlite3` собирается нативно и ломает `npm install` там, где нет готовой сборки, а встроенный `node:sqlite` появился только в Node 22, тогда как задание разрешает Node 20. JSON-файл снимает оба риска и прямо назван в задании как допустимый вариант. Чем он хуже: нет запросов и индексов, весь файл читается целиком, при тысячах ответов это станет заметно. Для одного проверяющего и десятков ответов разницы нет.

Формы, ответы и события лежат в отдельных файлах в `data/`. Запись идет во временный файл с последующим `rename`, а записи в один файл выстроены в очередь: без этого две одновременные отправки прочитали бы одно состояние и вторая затерла бы первую.
